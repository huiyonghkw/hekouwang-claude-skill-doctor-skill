# 触发力实测（trigger eval）· 怎么设计 query、怎么读结果

> 机检 #2 只能看出 description 里**有没有**"当…时/use when"这类信号词，判不出**写得准不准**。
> 这份文档配 `scripts/trigger_eval.py`，补的是那一层：真跑一遍，看模型会不会被这段 description 唤醒。
> ⚠️ 需要 `claude` CLI，**会产生真实费用**（每条 query 每次采样约 $0.09–0.15）。
> `check.py` 不依赖它，零依赖那条卖点不受影响。

## 0. ⭐ 跑之前必做：基准分辨力自检（不做就别信任何分数）

**先喂一个已知好的和一个已知烂的，看分数分不分得开。** 分不开说明这套判据在你的环境里失灵，
此时任何分数都是噪音——包括那个看起来很健康的高分。

```bash
# A 组：真 description
python3 scripts/trigger_eval.py --eval-set queries.json --skill-path <skill> --label A

# B 组：同一套 query，换一段故意写烂的 description
printf '生成内容。\n' > /tmp/bad-desc.txt
python3 scripts/trigger_eval.py --eval-set queries.json --skill-path <skill> \
  --description-file /tmp/bad-desc.txt --label B
```

**判据**：A 明显高于 B（实测参考：A=100 / B=50，4 条 query）才算这套 eval 在你机器上有效。
两组同分 = 判据失灵，先去查第 4 节。

> 这不是形式主义。开发本脚本时，前后四处配置错误里有**三处**都表现为
> "跑通了、只是分数低"——不做 A/B 根本发现不了，会拿一堆假分数去改 description。

## 1. eval query 怎么写

**数量**：20 条左右，正例 8–10、负例 8–10。想省钱可以先用 4–6 条粗筛，方向对了再补齐。

**质量三条**：

1. **写成用户真会打出来的一整段话**，不是抽象任务名。要有具体文件名、路径、栏目名、
   数字、背景交代，可以有口语、缩写、错别字、全小写。
   - ❌ `"生成小红书图文"`
   - ✅ `"帮我把这篇讲 uv 的文章做成一套小红书图文，8 张 1080x1440，用 V2 米白那套视觉，封面要有数字锚点"`

2. **正例要覆盖不同说法**。同一个意图，有正式的、有随口的；**要有几条不点名品牌/不提专有名词**
   的（"我写完一篇稿子想发公众号，帮我出文章母本和配图"）——这类最能检验 description
   有没有把使用场景说清楚，而不是靠关键词硬碰。

3. ⭐ **负例必须是 near-miss**。共享关键词或概念、但其实该走别的工具的请求，才有检验力。
   - ❌ `"帮我写个快排"`（对内容工厂来说太远，测不出任何东西）
   - ✅ `"帮我给这个 React 项目做个好看的产品落地页"`（同样是"做视觉"，但属前端）
   - ✅ `"帮我看下上周几篇小红书笔记数据，哪篇曝光最高"`（提了小红书，但是数据分析）

**别用的 query**：一步就能做完的简单请求（"读一下这个文件"）。模型对自己就能轻松搞定的事
本来就不查 skill，这种用例无论 description 写得多好都不会触发，纯粹浪费钱。

格式：

```json
[
  {"query": "……", "should_trigger": true,  "note": "正1·核心场景"},
  {"query": "……", "should_trigger": false, "note": "负1·near-miss 同是做视觉但属前端"}
]
```

## 1.5 ⭐ 负例必须带干扰项跑，否则结论是假的

探针环境默认**只有被测 skill 一个候选**。模型 `ls` 完发现没别的可选，
就会勉强用手头这个——**负例于是系统性假阳性**。

实测（content-factory · 同一套 6 条 query · 同一段 description）：

| 环境 | 得分 | 那条"翻页演示版网页"负例 |
|---|---|---|
| 无竞争者 | **83**（5/6） | ✗ 误触发 |
| 放 5 个兄弟 skill 当竞争者 | **100**（6/6） | ✓ 正确避开 |

**同一段 description，什么都没改，分数差 17 分。** 按 83 分那个数字去"修边界"，
修的是一个不存在的问题。

```bash
python3 scripts/trigger_eval.py --eval-set queries.json --skill-path <skill> \
  --distractors ~/.claude/skills/其它skill-A ~/.claude/skills/其它skill-B ...
```

选谁当干扰项：**功能相邻、最可能抢活的那几个**。自己有一套 skill 的话，
把兄弟们全带上最省事，也最接近真实环境。

⚠️ **干扰项的名字也被中性化成 `alt-xxx`，这是故意的**。若让干扰项挂真名
（`yandu-deck` 之类）而被测探针挂中性名，模型光看名字就能认出干扰项，
等于给对手开外挂——测出来的仍旧是名字不是 description，跟第 4 节第 4 条同一个坑。

> 正例也别忘了看：竞争者在场时正例**仍应触发**。若加了干扰项后正例掉了，
> 说明 description 的区分度不够，被邻居抢走了——这才是真该改的信号。

## 2. 怎么读结果

分数只是入口，**两种失败要分开看，修法完全不同**：

| 症状 | 含义 | 怎么改 description |
|---|---|---|
| **漏触发**（该触发的没触发） | 覆盖面不够，用户换个说法就唤不醒 | 补场景句和同义说法；把用户真实的口语表达写进去 |
| **误触发**（不该触发的触发了） | 写太宽泛，抢别的工具的活 | 加边界（"不用于 X"）；把泛词换成具体动作与产物 |

同时出现两种 = description 抓错了维度，重写而不是打补丁。

采样次数：默认 `--runs-per-query 1` 省钱。触发是概率性的，要下正式结论用 `3`
（成本 ×3），此时触发率 ≥0.5 判通过。

## 3. 结果不对劲时

先用 `--dump-dir` 把原始流存下来翻，**别猜**：

```bash
python3 scripts/trigger_eval.py ... --dump-dir /tmp/dumps
```

翻的时候重点看两样：模型的**工具调用序列**（它到底做了什么），
以及 Skill/Read 调用里的**实际参数**（是不是调到了别的东西）。
本脚本历史上两次假阴性都是靠翻这个抓出来的。

## 4. 脚本为什么这么写（改它之前先读这节）

本脚本改自官方 `anthropics/skills · skill-creator/scripts/run_eval.py`。
官方思路对，但原样跑在 Claude Code 2.1.220 上**测不出任何东西**。四处都改完才有分辨力——
**这四处是踩出来的，改脚本时别顺手改回去**：

1. **`--setting-sources project`**：不加则子进程继承 `~/.claude/skills/` 里已装的真 skill
   （实测 32 个），模型去触发真身、名字对不上探针 → 全部正例假阴性。
   官方没料到"被测 skill 已经装在机器上"这种情况。

2. **扫完整个流才判否**：官方是"第一个 tool_use 不是 Skill/Read 就 return False"。
   但模型碰到陌生 skill 名**会先 `Bash: ls` 探查环境**，Skill 往往是第二三个动作
   （实测序列 `['Bash','Bash','Skill']`）——真触发了却被判没触发。

3. **每条 query 独立 project root**：共用目录时并发 worker 把探针全丢一处，
   模型会调到**别人的**探针（实测：期望 `-d795b59f`，实际调 `-4ac07ae5`），自己这条判否。

4. ⭐ **探针要装成 project 级真 skill，且名字中性（`probe-xxxxxxxx`）**：
   init 事件里 `skills` 和 `slash_commands` 两个列表**都只给名字、不给 description**。
   探针一旦沿用原 skill 名，模型光看名字就去 Read 它，**description 全程没参与决策**——
   实测此时 447 字真 description 和 5 字"生成内容。"**都是满分**，等于白测。

## 5. 成本

| 规模 | 调用数 | 约合 |
|---|---|---|
| 粗筛 4 条 × 1 次 | 4 | $0.5 |
| 正式 20 条 × 1 次 | 20 | $2–3 |
| 结论 20 条 × 3 次 | 60 | $6–9 |

先粗筛、方向对了再上规模。A/B 基准自检要算两轮。
